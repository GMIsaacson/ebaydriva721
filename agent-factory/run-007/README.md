# Run 007 — Systems Intelligence & Development Team

## Purpose
Continuously identify missing capabilities, recurring friction, emerging risks, duplicated work, and high-value opportunities across the operating system before they become owner-visible problems.

Run 007 owns the mandatory **A0 Architecture Discovery Gate** and the global **Factory v2 lifecycle controls** for substantial Agent Team Factory work. Its job is to understand the complete system before the Factory optimizes one component inside it, and to convert reusable lessons from completed Runs into versioned Factory standards.

## Core loop
Observe → Detect → Evidence → Challenge → **A0 Architecture Discovery** → **B0 Run Boundary Contract** → Build/Test through G0–G5 → **D0 Downstream Readiness** → **C0 Outcome/Commercial Validation where applicable** → **P0 Production Readiness** → Controlled Activation → **R0 Retrospective / Global Patch** → Register Capability → Resume Observation

## Units
1. Systems Scout (Thinker)
2. Systems Architect (Planner)
3. Factory Orchestrator (Builder)
4. Challenger & Verification Agent (Reviewer)

## Authority
- Observe broadly across approved internal sources.
- Create internal discovery candidates and recommendations.
- Produce plans, system maps, run decompositions, contracts, readiness reviews, and build specifications.
- Patch Factory standards internally when a lesson is generalizable; material authority changes remain separately gated.
- No vendor action, spending, subscription/account changes, destructive actions, or external communication without separate explicit authorization.
- Builder routes approved work through existing Agent Factory; it does not create a parallel execution framework.

## Mandatory A0 rule
**No substantial new Factory Run may enter G0 until Run 007 records A0 = PASS.**

A0 must map the entire outcome/value chain, required capabilities, natural team/system boundaries, shared infrastructure, canonical data ownership, upstream/downstream contracts, dependencies, authority boundaries, operability, scale paths, and proposed Run sequence.

Trivial maintenance/bug fixes may be exempt only when the Challenger documents that the approved architecture is unchanged.

## Mandatory B0 rule
After A0 and before G0, each substantial Run must have a versioned **Run Boundary Contract** defining what the Run owns, what it explicitly does not own, its inputs/outputs, upstream/downstream contracts, canonical stores touched, authority ceiling, and completion condition.

A Run may not silently expand into adjacent responsibilities. Material boundary changes require an Architecture Amendment plus a new contract version.

## Dual readiness rule
Every major gate review reports separately:
- **Capability Readiness** — can the component perform its defined job?
- **System / Business Readiness** — can the surrounding end-to-end system produce the intended outcome?

A component may be validation-ready while the business/system remains incomplete.

## Mandatory D0 rule
A producer capability cannot be considered operationally complete for recurring use until its downstream consumer, durable destination/store, handoff contract, reject/remediation path, provenance, idempotency, and unresolved-output ownership are ready.

## Mandatory P0 rule
No unattended recurring production, automatic external delivery, or production authority until the complete relevant system passes the Production Readiness checklist: durable storage/lifecycle, health/staleness, retry/replay/idempotency, unknown-outcome handling, cost limits, quality telemetry, escalation, privacy/retention, credential boundaries, source-access constraints, kill switch, recovery, audit/provenance, KPIs, downstream readiness, and contract compatibility.

## Mandatory R0 rule
At major validation milestones and before production activation/closure, Run 007 performs a retrospective. Generalizable lessons become versioned **Factory Patches**, not local notes.

## Contract versioning rule
Material system maps, Run Boundary Contracts, handoff schemas, authority profiles, lifecycle contracts, scoring/policy contracts, delivery contracts, and production-readiness profiles must carry explicit versions. Breaking changes require impact review and revalidation of affected components.

- Purchase / Warranty Manager

## Success condition
Run 007 is successful when it produces and maintains a prioritized, evidence-backed capability roadmap that distinguishes:
- shared infrastructure to build once,
- modules/teams to build next,
- modules to defer,
- existing capabilities to reuse,
- risks or blind spots the owner has not yet identified,
- before each substantial Run, an approved A0 System Map Package and B0 Run Boundary Contract,
- before recurring operation, D0 downstream and P0 production evidence,
- and after material learning, an R0 decision on whether the Factory itself must be patched.

## Architecture amendment rule
If later evidence reveals a materially missing team, store, handoff, dependency, or authority boundary, Run 007 issues an Architecture Amendment and determines whether the current Run should be patched, a new upstream/downstream Run should be created, shared infrastructure should change, or further authority should pause. The amendment must identify affected contract versions and required revalidation.
